CogniLoad-XAI is a browser-based Muse 2 / Muse S (Classic protocol) EEG research workspace. The experiment page records four EEG channels (TP9, AF7, AF8, TP10) continuously through a configured baseline, a task, and a configured post-task rest, then exports one CSV per session.

The interface supports Thai and English. Use the **English / ไทย** button on the sign-in screen or in the app header to switch languages. The choice is saved in this browser and survives reloads. On first visit, the app chooses Thai for a Thai browser locale and English otherwise. Changing the interface language does not change recorded EEG data or CSV field names.

## Running a study session

1. Sign in with a researcher account. Use Chrome or Edge on a computer or Android device over HTTPS or `localhost`; allow Bluetooth access.
2. Enter a pseudonymous participant ID, session ID, participant group (`patient` or `control`), condition, choose one of the three web games, and set the maximum task duration (5 seconds up to the configured maximum). Confirm that consent has been obtained under the study protocol. Use the same game and task duration for corresponding sessions in both groups; run another session for another game.
3. Connect Muse and wait for the **EEG ครบ 4 ช่อง** indicator and live channel values. Research sessions require at least one second of recent data on each channel and block starting if at least 1% of recent samples on any channel reach the ADC limit. For a hardware check, use **ทดสอบอุปกรณ์ 15 วินาที**; the exported CSV will have `test_mode=true` and does not require participant consent or a quality precheck. A research session records the configured baseline before the game starts. EEG stays recording during the game and for the configured rest period after the game ends. Total planned duration is limited to 600 seconds.
4. Use **เพิ่ม marker** for additional events. Automatic markers identify session and phase boundaries. The selected game opens automatically at the start of the Task phase. Press **จบกิจกรรม · เก็บ EEG ต่อ** when the participant finishes, or let the task reach its maximum time. Either way, the game stops and the EEG continues for the configured post-task rest. The exported `task_seconds` reflects the elapsed task time. Game markers include game number, trial number, stimulus, response, correctness and reaction time; a game summary marker records total responses, errors and mean reaction time. Repeated clicks on a response are ignored. Leaving the game page during Task, failing to start the selected game, losing the device or one EEG channel, or hiding the tab stops the session and marks it incomplete; the partial recording remains exportable.
   Reaction time starts when the stimulus appears for Odd or Even and Pattern Drift. For Echo Sequence it starts when the response prompt appears, after the 2.2-second display period.
5. EEG and markers are saved in browser IndexedDB in short batches during recording. Each session also retains its own summary of timing, EEG sample counts and quality, and game results when available. Finalized summaries sync to the server for the admin view; the recording and CSV remain in this browser. If sync fails, the local list shows **Pending sync** and offers **Retry summary sync**. If the tab closes or reloads, the most recent saved batches remain available in **รอบทดลองที่เก็บในเครื่อง** and an unfinished session is marked interrupted. Up to roughly one second of unsaved data can be lost on an abrupt browser or operating-system crash. Export the CSV and check the downloaded file before starting another session. After exporting raw EEG, **ลบ EEG ดิบ เก็บสรุป** removes the large recording while keeping its summary for comparison. **ลบรอบถาวร** removes local data only; already synced server summaries remain available to admins. Clearing site data or using another browser/device removes access to locally saved sessions.

The local recording list and Dashboard show only sessions assigned to the signed-in researcher. Older local sessions without an owner are kept separately and never sync automatically. After checking ownership, use **Older recordings without an owner → Assign to this account**, review the session, then select **Retry summary sync**. A browser profile is not a secure boundary for raw EEG: use separate browser or operating-system profiles for different researchers, and protect exported CSV files according to the study's data policy.

The CSV has one header and one row per EEG sample or event marker. Every row includes `study_group`, `game_id` and `protocol_version` (`alz_web_games_v1` by default for a research session). `timestamp_ms` for EEG is the host-clock estimate from `muse-jsx`, with sample offsets at 256 Hz; event markers use the browser clock. `received_at_ms` records packet arrival time. `relative_ms` is relative to session start. `packet_index` and `sample_index` help identify dropped or reordered packets. The screen shows observed samples per second and estimates missing, duplicated, and reordered packets from the 16-bit Muse packet index independently for each channel. No EEG recording is sent to the server by this workflow.

The **Dashboard** tab reads the signed-in researcher's recordings from this browser's IndexedDB. Its overview charts show completed research sessions: the bar chart compares EEG sample counts across TP9, AF7, AF8 and TP10 for the latest completed session; the pie chart shows its actual baseline, task and post-task durations; and the line chart tracks average samples per second per channel across up to 12 completed sessions. Below the charts, **สรุปผลทุกครั้งที่ทดลอง** lists every saved session for this account, including incomplete runs and device checks. Choose any two sessions to compare their timing, EEG counts and quality, and game performance side by side. **ส่งออกสรุปทุกครั้ง (.csv)** downloads one row per session for backup or analysis. Earlier recordings are summarized when the dashboard first loads them. The older assessment overview remains available in a collapsible section below the EEG charts.

## Admin view

Set `ADMIN_USERS` on the server to a comma-separated list of `email:password` pairs (passwords must be at least 12 characters), for example `ADMIN_USERS='admin@example.org:replace-with-a-long-secret'`. Admin accounts are configured by the server operator; public registration cannot grant admin access. Set a stable `SESSION_SECRET` as well. After signing in, open **Admin**, search a pseudonymous participant ID, and select it to see all synced session summaries, including incomplete runs and device checks. The comparison table lets you compare any two runs for that ID, and the CSV button exports those summaries. Each summary records the researcher account that uploaded it. The admin API requires an authenticated admin account for both the ID list and record details; researchers can only upload summaries. Raw EEG and event rows are never uploaded by this feature.

With `DATABASE_URL`, researcher accounts, synced summaries and study settings are stored in Neon Postgres. Tables are created on first use. Without `DATABASE_URL`, these are stored as JSON under `COGNILOAD_DATA_DIR` (default: `data/`) for a single local server. The older `RESEARCH_DATA_DIR` still redirects only research summaries. Vercel requires `DATABASE_URL` and `SESSION_SECRET`; it will not fall back to JSON storage. Back up the database and any local files before changing storage. Summary sync runs when the owner signs in and after each finalized session. Older unassigned local sessions require explicit assignment before sync. Admins only see records after sync succeeds.

To move existing local JSON accounts, summaries and saved study settings into Neon, run `node scripts/migrate-local-json.mjs` on the machine that holds the JSON files. This checks the files and prints counts without writing to Neon. Then set `DATABASE_URL` to the target database, keep `COGNILOAD_DATA_DIR` and any `RESEARCH_DATA_DIR` pointed at the original files, and run `node scripts/migrate-local-json.mjs --apply`. The import creates only missing rows; existing database rows and settings keep their values. It can be rerun after an interrupted import. Verify account sign-in, admin summaries and study settings against the target deployment before retiring the local files. Browser IndexedDB EEG recordings and CSV files are outside this import.

## Server settings

Put these variables in the server environment or a local `.env` file. Restart the server after changing them. An authenticated admin can edit study timing and protocol in the **Admin → Study settings** form. Those values are saved in the selected persistent store and take precedence over environment defaults until the admin selects **Restore server defaults**. The page refreshes settings when refocused and checks again when a session starts; a recording already in progress keeps its starting values. `/api/config` exposes only public study settings and registration status.

| Variable | Default | Purpose |
| --- | --- | --- |
| `DATABASE_URL` | unset | Neon Postgres connection string for persistent storage on Vercel. |
| `COGNILOAD_DATA_DIR` | `./data` | Local JSON directory when `DATABASE_URL` is unset. |
| `RESEARCH_DATA_DIR` | unset | Legacy override for summaries only; `COGNILOAD_DATA_DIR` takes precedence. |
| `SESSION_SECRET` | generated in local data directory | Stable cookie signing secret; required on Vercel and at least 32 characters in production. |
| `ADMIN_USERS` | empty | Comma-separated `email:password` administrator accounts; passwords at least 12 characters. |
| `RESEARCHER_USERS` | empty | Preconfigured researcher accounts as comma-separated `email:password` pairs; passwords at least 12 characters. |
| `DEMO_USERS` | empty | Legacy demo accounts; use `RESEARCHER_USERS` for new deployments. |
| `REGISTRATION_ENABLED` | `false` in production, `true` in development | Allow public researcher account creation; set explicitly to `true` or `false`. |
| `STUDY_BASELINE_SECONDS` | `30` | Baseline length, 1–300 seconds. |
| `STUDY_POST_TASK_SECONDS` | `30` | Post-task rest length, 1–300 seconds. |
| `STUDY_MAX_TASK_SECONDS` | `540` or remaining time | Maximum task length, 5 seconds up to `600 - baseline - rest`. |
| `STUDY_DEFAULT_TASK_SECONDS` | `60` or task maximum | Initial task length, 5 seconds up to the task maximum. |
| `STUDY_PROTOCOL_VERSION` | `alz_web_games_v1` | Identifier recorded in raw and summary CSV; change it when the study procedure changes. |

Invalid study values make `/api/config` return an error and prevent starting a recording until corrected. The 15-second device check keeps its fixed timing. Existing recordings keep their original timing and protocol identifier.

The screen also warns when at least 1% of samples in a channel reach the Muse ADC limit (about ±1000 µV). This indicates clipped values; the channel needs a contact/fit check before participant recording. For an exported file, run:

```bash
node scripts/validate-muse-csv.mjs /path/to/muse_recording.csv
```

The validator prints phase timing, samples per channel, packet gaps, clipping percentages, an approximate 50 Hz amplitude from two-second windows, and game trial markers. A 50 Hz warning is a heuristic for possible mains interference, not a clinical signal-quality cutoff. The live graph centers each channel on its recent mean and uses an automatic display scale; neither operation changes the raw EEG in the CSV. The four large numbers are the latest raw samples, so their signed values can drift and are not scores. `unansweredTrials` identifies stimuli without a response, including a trial cut off by the Task deadline; analyze these separately. It reports data integrity and basic signal checks, not clinical EEG quality or an Alzheimer diagnosis.

This is a research prototype; signal display and sample counts do not establish clinical signal quality or a diagnosis. Validate timing and data completeness against your study protocol before collecting participants.

## Start and deploy

For local development run `npm install` and `npm run dev`, then open `http://localhost:3000`. Copy `settings.example.env` to `.env` and replace its placeholders, or set the same variables in your process manager.

### Vercel and Neon go-live

1. Push the reviewed project files to GitHub and import the repository as a Vercel project. The repository root is the app root. `vercel.json` selects `npm ci` for reproducible installs even if a pnpm lockfile is present.
2. From the Vercel project, install the [Neon integration](https://vercel.com/marketplace/neon/neon) and connect it to Production. Use a separate Neon branch for Preview deployments. Confirm that `DATABASE_URL` is present in each intended [Vercel environment](https://vercel.com/docs/environment-variables/manage-across-environments); the application requires it on Vercel.
3. Add a stable `SESSION_SECRET` of at least 32 characters, `ADMIN_USERS` and `RESEARCHER_USERS` in the Vercel environment settings. Keep `REGISTRATION_ENABLED=false` unless public researcher sign-up is intended. Generate the secret locally with `openssl rand -base64 32` and enter it directly in Vercel; do not commit it. Use the same secret across redeployments of one environment so existing sessions remain valid.
4. Redeploy after connecting Neon or changing environment variables. Visit `/api/config`; expect HTTP 200 with the configured study values. Sign in as an admin, change a study value in **Admin**, reload, and confirm it remains saved. Restore the intended production value. Sign in as a researcher and confirm the experiment page shows those values.
5. On a computer with a real Muse, run a 15-second device check, export and inspect its CSV, then test one consented research session under the study protocol. Confirm the researcher's summary syncs and appears in Admin after a reload. The raw EEG is stored only in the researcher's browser until exported; back up each CSV according to the study's data policy. Confirm that accounts, settings and summaries remain after a fresh deployment before collecting participant data.

The server creates its Postgres tables when the first request needs them. For a single-server deployment without Neon, run `npm run build` then `npm run start` behind HTTPS with a persistent writable data directory. Accounts use scrypt password hashes and sessions use HMAC-signed cookies.
